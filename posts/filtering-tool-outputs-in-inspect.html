What’s the right way to filter tool outputs in Inspect?

evals
inspect
tooling
I went looking for a sanctioned way to filter what a tool returns, and couldn’t find one. Notes on what I tried, a hook that fails open silently, and the pattern I settled on.
Published

August 21, 2026

The claim

Every eval makes an implicit claim about what the model had access to. With a fixed dataset that claim is easy to keep — you shipped the data, so you know. Give an agent a live tool and the claim stops being a property of the task and becomes a property of the harness: it now depends on what the harness let through.

Inspect has no dedicated mechanism for this. Approval runs before the tool does and can only rewrite the call. Nothing documented sits between the result and the model. And the hook that looks like the right place fails open silently — if your filter raises, the model gets the unfiltered result and the run reports success.

This post is about where that matters, what I tried, and what I think would help. The short version: I’ve been wrapping ToolSource, it works, and I’d like to know whether that’s the intended answer or whether I’m solving a problem Inspect deliberately doesn’t have.

Why bound tool output at all

  • Eval integrity. Reference solutions, graders, hidden tests and answer keys have to stay out of tool responses. If an agent can reach them, the score measures retrieval rather than capability — and the result is not merely noisy, it is void. A capable agent will route around controls it can see, so the boundary has to hold outside the agent’s reach, not by instruction; the quiet version of the same failure is mundane — a search tool that happens to surface a writeup of the task.
  • Controlled-information evals. A large class of safety questions have the shape “what does the model do when it has exactly this information and no more?” — sandbagging and underperformance work, situational-awareness probes, scenarios testing whether an agent acts on material it should not have. The information boundary is the experimental condition.
  • Dangerous-capability elicitation. Sometimes you want the agent to have a realistic tool while specific content is withheld, and to measure whether it tries — which requires filtering the result, not blocking the call.
  • Contamination control. Temporal gating is one instance: dropping results dated after a decision point so a task is not trivially answerable from leaked future data.

What these have in common is that they’re output-level — the call is legitimate, and it’s the result that needs bounding. They also want to fail closed: a control that silently doesn’t apply gives you a clean-looking result you can’t distinguish from a valid one, which seems worse than an error.

That’s the part I couldn’t find a sanctioned answer for.

The obvious alternative: curate the corpus instead

Before going further it’s worth saying that there’s a good answer to all of this which doesn’t need any framework support: don’t filter at runtime, control the corpus up front. Build the document set the agent can reach, serve only that, and the boundary is guaranteed by construction. Most inspect_evals tasks run on fixed datasets; agentdojo goes further and simulates the tool backends entirely; sandboxes default to network_mode: none. If your eval fits that shape, curation is strictly better than filtering — fewer moving parts, and nothing to fail open.

I think it stops fitting in four places, and I’d be glad to be wrong about any of them.

Eval-awareness. A conspicuously synthetic corpus is a tell. A model that infers it is being evaluated may behave differently — which is exactly the effect a lot of safety evals are trying to measure without contaminating. A real tool returning a filtered result is a smaller tell than an obviously fabricated document set. This is a hypothesis rather than something I’ve measured, but it seems like the case where curation is most costly.

External validity of the tool. If part of what you’re measuring is how an agent copes with noisy, contradictory or partly-wrong results, a clean curated corpus has removed the phenomenon.

Open-ended browsing. Once an agent can follow a link, curation means the transitive closure of whatever it can reach. That isn’t expensive so much as undefined.

Third-party services you don’t control. A live database, a code-execution backend, someone else’s MCP server. You can’t curate its responses. Filtering them is the only lever.

None of this makes curation wrong — it makes it a different point on a trade-off. And if the answer is that Inspect is deliberately aimed at the curated end, that’s worth knowing explicitly, because it changes what you build rather than how you build it.

What I found

Approval is call-only. Approval.modified is ToolCall | None, and the Approver signature takes (message, call, view, history) — the result doesn’t exist yet when an approver runs.

Nothing sits between execution and the model. The result is returned unmediated, apart from size truncation.

Wrapping ToolSource does work. Re-wrapping each ToolDef so the wrapper awaits the inner tool and filters the result before returning it gives an output-level control that fails closed, and it composes over MCP servers since MCPServer subclasses ToolSource. That’s what I’ve been using. I couldn’t find this pattern documented, hence the question.

The one I tried first: on_before_model_generate

This is the hook I reached for first, and I don’t think I’d be the only one. docs/extensions-hooks.qmd:90 says mutating inputs there “is explicitly supported and intended”, and data.input does flow into the provider call — so it reads like the sanctioned place to transform what the model sees.

Three paragraphs later, line 93 notes that “any exception raised by a hook is caught and logged as a warning (it does not fail the run)”, implemented at _hooks.py:1094-1104.

Both facts are documented; they’re just never connected. Composed, they mean a filter implemented as a hook fails open silently — the model receives unfiltered input and the run reports success. Repro on inspect-ai==0.3.258 (no API key; mechanism identical at main 331e2b0):

The second arm — same hook, mutating in place instead of raising — confirms the mechanism works. So the first arm is a silent failure, not a broken hook.

I’m not suggesting hooks should propagate exceptions; a crashing observer shouldn’t abort a run, and that’s clearly deliberate. The narrow point is that the “explicitly supported and intended” line reads as an invitation to build controls there, and the consequence isn’t stated next to it.

Full repro (python fail_open_repro.py, no API key) 
"""
Fail-open demonstration for Inspect's on_before_model_generate hook.

Claim: a data-access gate implemented as an `on_before_model_generate` hook
(the pattern the docs bless: "mutate data.input") SILENTLY FAILS OPEN. If the
gate raises, Inspect's `_emit_to_all` swallows the exception to a
`logger.warning` and the eval CONTINUES with the model receiving the
UNREDACTED input. The run reports success. Nothing signals the control was skipped.

Run against installed inspect_ai 0.3.258; mechanism verified identical at main @ 331e2b0
(2026-08-20):
  - _emit_to_all  src/inspect_ai/hooks/_hooks.py:1094-1104  (L1101-1102 re-raises
                  LimitExceededError; L1103-1104 swallows everything else to
                  logger.warning) -> hook exceptions are swallowed.
  - dispatch      _hooks.py:894  on_before_model_generate
  - BeforeModelGenerate.input is the SAME list object later sent to the provider
    (_model.py:1291), so an in-place mutation flows through -- proving the gate
    CAN work; the failure is specifically the silent one.

Two arms:
  RAISE  -> gate raises before redacting  -> secret REACHES the model, run succeeds.
  REDACT -> gate mutates input in place    -> secret is removed (mechanism works).

Run:  python fail_open_repro.py     (no API key needed; uses mockllm/model)
"""

import logging
import tempfile

from inspect_ai import Task, eval, task
from inspect_ai.dataset import Sample
from inspect_ai.hooks import BeforeModelGenerate, Hooks, hooks
from inspect_ai.solver import generate

SECRET = "SECRET-DATA-AFTER-CUTOFF"

# Behaviour toggle, read at hook-call time. Set by run_arm() below.
GATE_MODE = "raise"


@hooks(name="redaction_gate", description="Redacts SECRET from model input (fail-open demo)")
class RedactionGate(Hooks):
    async def on_before_model_generate(self, data: BeforeModelGenerate) -> None:
        if GATE_MODE == "raise":
            # A realistic filter failure: an exception before redaction completes.
            raise RuntimeError("gate failed: filter raised before redacting")
        # Correct usage: mutate the shared message objects IN PLACE.
        for msg in data.input:
            if isinstance(msg.content, str) and SECRET in msg.content:
                msg.content = msg.content.replace(SECRET, "[REDACTED]")


@task
def leak_task():
    return Task(
        dataset=[Sample(input=f"Here is confidential material: {SECRET}. Summarize it.")],
        solver=generate(),
    )


class WarningCatcher(logging.Handler):
    def __init__(self):
        super().__init__(level=logging.WARNING)
        self.records = []

    def emit(self, record):
        if "Exception calling hook" in record.getMessage():
            self.records.append(record.getMessage())


def model_input_text(log):
    """Extract the input the model actually received, from the ModelEvent."""
    for sample in log.samples or []:
        for ev in sample.events or []:
            if getattr(ev, "event", None) == "model":
                return str(ev.input)
    return "<no model event found>"


def run_arm(mode):
    global GATE_MODE
    GATE_MODE = mode

    catcher = WarningCatcher()
    # inspect_ai sets propagate=False on its package logger and installs its own
    # handler (see _util/logger.py), so attach directly to that logger.
    pkg_logger = logging.getLogger("inspect_ai")
    pkg_logger.addHandler(catcher)
    if pkg_logger.level > logging.WARNING or pkg_logger.level == logging.NOTSET:
        pkg_logger.setLevel(logging.WARNING)
    try:
        with tempfile.TemporaryDirectory() as d:
            logs = eval(leak_task(), model="mockllm/model", display="none", log_dir=d)
            log = logs[0]
            # Extract while the log dir still exists (samples are read lazily).
            seen = model_input_text(log)
            status = log.status
    finally:
        pkg_logger.removeHandler(catcher)

    return {
        "status": status,
        "hook_raised": len(catcher.records) > 0,
        "warning": catcher.records[0] if catcher.records else "(none)",
        "secret_reached_model": SECRET in seen,
    }


if __name__ == "__main__":
    print("=" * 78)
    print("Inspect on_before_model_generate — fail-open demonstration")
    print("=" * 78)
    for mode, label in [
        ("raise", "GATE RAISES (filter fails)"),
        ("redact", "GATE REDACTS (works)"),
    ]:
        r = run_arm(mode)
        print(f"\n[{label}]  mode={mode!r}")
        print(f"  eval status ............ {r['status']}")
        print(f"  hook raised ............ {r['hook_raised']}")
        print(f"  warning logged ......... {r['warning']}")
        print(f"  SECRET reached model ... {r['secret_reached_model']}")
    print("\n" + "=" * 78)
    print("If the RAISE arm shows: status=success, hook raised=True, SECRET reached=True,")
    print("then the gate failed open silently — the eval passed with the control skipped.")
    print("=" * 78)

What I’d suggest

In rough order of how much I’d be asking for:

  1. A one-line cross-reference in the hooks docs. extensions-hooks.qmd:90 blesses mutating data.input; line 93 notes hook exceptions are swallowed. Both are true and three paragraphs apart. A pointer from the first to the second — “hooks are observers and fail open, so don’t use them for correctness-critical filtering” — would have saved me the detour. Happy to PR this today if it’s wanted.

  2. A documented answer on the intended pattern. If ToolSource wrapping is it, saying so in the tools docs makes it discoverable; tools-custom.qmd currently covers tool_with(), ToolDef and error handling but nothing about transforming a result. Also happy to PR.

  3. Only if there’s appetite: a first-class, fail-closed output interception point. The OpenAI Agents SDK has @tool_output_guardrail, which runs after the tool executes and can replace the output or trip a wire. I’m not suggesting Inspect should copy it — just that the shape recurs, and a sanctioned hook would fail closed by construction rather than by convention.

If the answer is instead “curate the corpus; runtime filtering isn’t the model here”, that’s a good answer and worth stating explicitly, because it changes what people build rather than how.

Where this came from

I built a small point-in-time probe — an agent answering “as of” a cutoff date with retrieval restricted to sources published before it, to separate what a model can work out from what it already remembers. That turned up the Exa provider crash I filed as #4911 and fixed in #4913. This is the other thing it turned up.

I’m not building a benchmark on this and I’m not proposing one — the probe was a few days’ work, and the question above is what it left behind.

The open question

Is ToolSource wrapping the intended pattern, something I’ve missed, or a sign that runtime filtering isn’t how Inspect expects this to be done? Any of those is a useful answer, and I’d rather build on the sanctioned thing than on a workaround I happened to find.
